## 0. READ THIS FIRST — THERE IS A LIVE REGRESSION IN PRODUCTION

**Symptom (reported by Jeff, 2026-08-15 evening): his phone shows him at a location ~2 hours
away from where he actually is.**

**Cause — VERIFIED by reading the code, and it was introduced by me on 2026-08-15:**

`src/locationPrivacy.ts:155`
```ts
function carAttached(): boolean {
  return _carConnected && Date.now() - _carConnectedAt < CAR_CONNECT_TTL_MS;  // 90_000
}
```
`shareablePosition()` computes `inCar = carAttached() || movingNow`. **If neither is true it
publishes `_carSpot` — the last recorded car spot — instead of the live position.**

Before 2026-08-15, `_carConnected` was a **latch**: set true, stayed true until explicitly
cleared. I changed it to a claim that **expires after 90 s** unless re-asserted. The only thing
that re-asserts it is an effect keyed on `[carConnected, coords?.lat, coords?.lng]`
(`app/(app)/map.tsx:3462-3464`). **When coordinates stop updating — phone stationary, screen
off, app backgrounded — nothing re-asserts, the flag lapses after 90 s, and the published
position falls back to a car spot that can be hours old.**

**The fix that was agreed but NOT YET APPLIED** (Jeff picked option 1; the session ended before
it shipped): the 90 s expiry exists because **Android** could not hear a disconnect event before
build 71. **iOS can** — CarPlay emits `didDisconnect` reliably. So the TTL should be an
Android-only backstop, and on iOS the flag should not expire. That restores the live position
while keeping the privacy fix that stopped Android broadcasting raw GPS.

⚠ Do NOT simply revert `locationPrivacy.ts` wholesale — the same commit closed a real privacy
hole (see §3). Fix the TTL platform gate specifically.

## 3. WHAT ACTUALLY GOT FIXED (so the next session does not undo it)

All of these were specced by one agent and adversarially re-verified by a second; rejected
edits were dropped. Do not revert them casually.

- **Android boot brick guard.** `registerAndroidAuto` evaluated the whole car module tree with
  no try/catch (the iOS twin had one). A module-scope throw there kills the app at boot →
  expo-updates ErrorRecovery → rollback to embedded → **the device can no longer be reached by
  OTA at all.**
- **Android was broadcasting raw GPS with no car attached.** `CarPlayModule.kt:96-98`'s
  `checkForConnection()` emits `didConnect()` **unconditionally**, so `CarPlay.connected` is true
  on every Android launch. That told the privacy gate a head unit was present. Also closed a
  second, ungated writer of `convoy.lastCarSpot.v1` that was persisting the walking position to
  disk. (This is the same commit that carries the §0 regression — fix the TTL, keep the rest.)
- **Android Auto Search never worked, at all.** Two stacked defects: our `getLib()` is iOS-only
  so the template was never created, AND the library's JS `SearchTemplate` forwards results to
  native only `if (Platform.OS === 'ios')` — on Android the results are computed and discarded.
  Android now drives the native `@ReactMethod`s directly.
- **Android Auto car pointed due north at every stop.** Android's expo-location has no
  `hasBearing()` gate, so a bearing-less fix arrives as heading `0` and every `>= 0` guard
  accepted it. Changed to `> 0` on the 7 heading writes; speed guards deliberately left alone
  (0 is a legitimate speed).
- **Car HUD ownership.** `maneuverIcon` and the route ribbon fields were written outside the
  `claimCarNavStrip` gate, so the warm mirror erased the cold engine's arrow (~1 Hz flicker) and
  the green route line vanished on car-started routes.
- **139 KB of dead base64 car art** + ~705 lines of dead code removed.
- **Android Auto basemap scale** — and it turned out to be **OTA-able, not native** (see §5).

## 4. HEAT — THE ANSWER, AND WHAT TO DO ABOUT IT

Full analysis: `WHY-IT-HEATS.md` (produced 2026-08-16, in the scratchpad; re-derive if lost).

### The headline — VERIFIED
**We compute the car's position and the camera in JavaScript, one frame at a time. Apple Maps,
Google Maps and Waze hand the map engine a target and a duration and let the engine draw the
in-between frames on its own render thread.**

**The Mapbox SDK already ships exactly what we hand-built.** VERIFIED in
`ios/Pods/MapboxMaps/.../Location/LocationManager.swift:184-201`: a `ValueAnimator` with a
**1.1 s position interpolator and a 0.3 s heading interpolator**, driven by the map's own display
link. `SelfCarModel`'s ease duration is `max(220, fixGap * 1.1)` — **we rewrote the SDK's own
animation in JS.** And we explicitly switch the native one off: both maps pass
`animationDuration: 0, animationMode: 'none'`.

### The work budget — counts are exact, cost-per-count is not measured
| Per second | Today | Could be |
|---|---|---|
| rAF frame loops (phone + car) | 120 | 0 |
| Native camera commits (JSON encode in JS → JSON decode in native) | 120 | 2 |
| React renders + Fabric commits of the car subtree | 120 | 0 |
| GeoJSON source replacements for a ONE-POINT feature | 120 | 0 |
| Location + heading pushes into the SDK's own interpolator | 240 | 2 |
| `BridgeValue` allocations from two ModelLayer style objects | ~16,200 | ~0 |
| Full re-renders of a ~1,500-line component (12 Hz ticker ×2) | 24 | ≤2 |
| **GL contexts drawing at 60 fps** | **2** | **2 — UNCHANGED** |

**~770 JS-originated native operations per second → ~8.** A full JSON round-trip **60–120 times
a second to move the camera 46 cm**.

### Why build 73's 60fps made it worse — VERIFIED
`HairpinSystemModule.swift:96` doubled the CarPlay `CADisplayLink` from 30 → 60. **For a native
app that doubles drawing. For us it doubled SCRIPTING and changed drawing not at all** — the car
map was *already* drawing at 60 because Mapbox binds its display link to the CarPlay screen
(`MapViewDependencyProvider.swift:88`). Build 73 doubled 60 native→JS pump events per second that
hit a 150 ms guard and immediately return. **We doubled no-ops.**

### ⚠ THE HONEST LIMIT
This explains the **scripting** load, which is counted exactly. It does **NOT** explain the GPU
load. We run **two complete map engines** (two `CoreMap`s, two Metal views, two tile pipelines)
and nothing gates the phone one. **None of the software fixes remove that.** Anyone who claims to
know whether JS or GPU is the heat, without the measurement in §4.1, is guessing.

Also unmeasured: `app.json` sets `CADisableMinimumFrameDurationOnPhone` and RN's display link caps
nothing, while both MapViews are pinned to `preferredFramesPerSecond={60}`. **HYPOTHESIS: rAF may
be running at 120 Hz into maps that only present 60, so half that work is discarded before it is
drawn.** That is a 2× factor on every number above. **Not measured.**

### 4.1 THE MEASUREMENT THAT SETTLES IT — already shipped, just needs a drive
`src/heatProbe.ts` ships in OTA `eac961f9`. One `heat-probe` row per 60 s of guidance:
- `raf=` — ~3600 means 60 Hz, ~7200 means **120 Hz and the budget doubles**.
- `dtP50/dtP95` — rAF interval percentiles; P95 exposes stalls (a stall IS a visible camera
  stutter today, because the pose is computed on the stalling thread).
- `cam=` / `tick=` — camera pushes and React commits actually made.
- `batt=` — level and charging state. **Level FLAT or FALLING while state=`charging` is iOS
  refusing the charger** — the exact reported symptom, captured automatically.

**And the decisive experiment needs no drive.** Driveway, engine off, CarPlay connected, same
brightness, 15 minutes each:
- **Run A:** stationary on real GPS — the 6 cm sub-pixel skip fires, JS pose work ≈ 0, both GL
  contexts still drawing.
- **Run B:** synthetic 100 km/h fix replay — JS work at full rate, GL identical.

**B hot + A cool → the JS loop is the heat, and the §5 plan fixes it. Both equally hot → it is the
two GL contexts plus the always-on screen, and no JavaScript surgery will help.**
